`root` can do anything. Nobody should log in as root; instead **sudo** lets named people run named commands as root, with their own password, and **logs every use**. Designing and reviewing sudo rules is daily privileged-access work.

## How a sudo rule reads

```text
%helpdesk  ALL = (root)  /usr/bin/systemctl restart falcon-web.service
   WHO     HOST  AS-WHOM  WHICH COMMAND(S)
```
- **WHO**: a user (`dpatel`) or a group (`%helpdesk`).
- **HOST**: `ALL` here; rules can be shared across servers.
- **AS-WHOM**: `(root)`, or `(ALL)` for any user. `(ALL:ALL)` also allows any group.
- **COMMANDS**: full paths. With arguments listed, **only those exact arguments** are allowed. Without arguments, **any** arguments are allowed.
- `NOPASSWD:` before the command skips the password prompt - acceptable for automation, risky for people.

Ubuntu's default `/etc/sudoers` contains `%sudo ALL=(ALL:ALL) ALL`: members of group `sudo` are full administrators. Extra rules live as separate files in `/etc/sudoers.d/` (file names must not contain `.` or end in `~`, and files must be mode `0440`).

## Always edit with visudo

```linux
sudo visudo -f /etc/sudoers.d/50-helpdesk-falcon
```
`visudo` locks the file, opens an editor (nano here) and **refuses to save a file with a syntax error** ("What now?" - press `e` to edit again, `x` to discard). Editing sudoers files with a plain editor can break sudo for everyone.

```linux
sudo visudo -c
```
Checks every sudoers file and prints `parsed OK` for each.

## Who can run what?

```linux
sudo -l
sudo -l -U dpatel
sudo -l -U dpatel /usr/bin/systemctl stop falcon-web.service
getent group sudo
sudo grep -rv '^#' /etc/sudoers /etc/sudoers.d/ | grep -v '^\S*:$'
```
- `sudo -l` lists your own rights; `-U USER` lists someone else's (needs root).
- Adding a command after `-l -U USER` asks "may USER run exactly this?" - it prints the command if yes, nothing and exit code 1 if no.
- Do not forget group-based rights: members of `sudo` (and `admin` on old systems) are full admins.

## Dangerous rules (privilege escalation)

Many programs can start a shell or write any file. Allowing them via sudo is the same as giving full root:
- editors: `vim`, `vi`, `nano`, `less`, `more` (`:!bash` in vim)
- `find` (`-exec`), `awk`, `tar` (`--checkpoint-action`), `rsync` (`-e`), `cp`/`tee`/`dd` (overwrite `/etc/sudoers`)
- `systemctl` **without** fixed arguments, `bash`, `sh`, `su`, `python3`, wildcards (`*`) in arguments

Prefer fixed commands with fixed arguments, or `sudoedit` for file edits.

## Logging

Each sudo use is logged:
```text
Nov 11 10:12:01 iamlab01 sudo:   dpatel : TTY=pts/1 ; PWD=/home/dpatel ; USER=root ; COMMAND=/usr/bin/systemctl restart falcon-web.service
Nov 11 10:13:44 iamlab01 sudo:   dpatel : command not allowed ; TTY=pts/1 ; PWD=/home/dpatel ; USER=root ; COMMAND=/usr/bin/systemctl stop falcon-web.service
```
`sudo journalctl _COMM=sudo` or `sudo grep 'sudo:' /var/log/auth.log`.

## If you lock yourself out

Practise changes in a **second** terminal and keep the first one open with a working `sudo -s` until you have tested. If sudo is broken anyway:
- real servers: console access, recovery mode, or another administrator;
- this lab: **Progress & lab tools > Fix broken sudo policy** in the portal, or `lab rescue sudoers` - a logged break-glass action that quarantines invalid files.
