Large organisations do not create accounts on every server. People live in a **directory** (Active Directory, FreeIPA, OpenLDAP, Entra ID via a bridge) and Linux servers **look them up**. This module uses the lab's own small OpenLDAP directory `dc=iamlab,dc=test` running **inside the lab VM** - it is disposable, contains only fictional people, and is completely separate from any other lab or server you have.

## Three questions on every login

| Question | Called | Linux component |
|---|---|---|
| *Who is "pshah"? What UID, groups, home?* | identity lookup | **NSS** (Name Service Switch), `/etc/nsswitch.conf` |
| *Is this really pshah?* (password, key, MFA) | **authentication** (authN) | **PAM** `auth` phase, `/etc/pam.d/` |
| *Is pshah allowed in here, now?* | **authorization** (authZ) | PAM `account` phase, sshd `AllowGroups`, sudo rules, file permissions |

A correct password with "access denied" is an **authorization** failure, not an authentication failure - an important distinction when you triage tickets.

## NSS

```linux
grep -E '^(passwd|group|shadow)' /etc/nsswitch.conf
```
```text
passwd:         files systemd sss
group:          files systemd sss
shadow:         files systemd sss
```
Sources are tried left to right: local files, then systemd's dynamic users, then **sss** (SSSD). `getent passwd NAME` uses this chain; `getent -s files passwd NAME` or `-s sss` asks one source only.

## PAM

Each program that authenticates has a file in `/etc/pam.d/` (`sshd`, `sudo`, `login`, `su`...). Most include the shared stacks:

| Stack | Typical modules here |
|---|---|
| `common-auth` | `pam_faillock` (lockout), `pam_unix` (local passwords), `pam_sss` (directory passwords) |
| `common-account` | `pam_unix` (expiry), `pam_sss` (SSSD access rules) |
| `common-session` | `pam_mkhomedir` (create home at first login), `pam_systemd` |
| `common-password` | password changes |

Each line has a **control** (`required`, `requisite`, `sufficient`, `[success=1 default=ignore]`) that decides what happens on success or failure. Do not hand-edit these stacks on Ubuntu; use `pam-auth-update`. A broken PAM stack can lock **everyone** out.

## SSSD

**SSSD** (System Security Services Daemon) connects NSS and PAM to the directory, caches results, and enforces access rules. Config: `/etc/sssd/sssd.conf` (must be mode `600`). In this lab:

```ini
[domain/iamlab.test]
id_provider = ldap            # identities from LDAP
auth_provider = ldap          # passwords checked by binding to LDAP
access_provider = simple      # authorization rule:
simple_allow_groups = linux-login   # only this directory group may log in
ldap_uri = ldap://ldap.iamlab.test
ldap_id_use_start_tls = true  # encrypt (StartTLS) and verify the server certificate
```

Useful commands: `sudo sssctl domain-status iamlab.test`, `sudo sssctl user-checks USER` (runs the PAM checks for a user), `sudo sss_cache -E` (forget cached entries - after directory changes), `sudo journalctl -u sssd`.

## LDAP in brief

The directory is a tree of entries, each with a **DN** (distinguished name), e.g. `uid=pshah,ou=people,dc=iamlab,dc=test`. Users have `uid`, `uidNumber`, `gidNumber`, `homeDirectory`, `loginShell`; POSIX groups list members as `memberUid`.

```linux
ldapsearch -x -ZZ -H ldap://ldap.iamlab.test -b dc=iamlab,dc=test '(uid=pshah)' uid uidNumber title
```
- `-x` simple authentication (here anonymous), `-ZZ` require StartTLS, `-H` server URI, `-b` search base, then a **filter** and the attributes to return.

Changes are written as **LDIF** with `ldapmodify`, binding as an administrator (`-D DN -y passwordfile`). In this lab, members of `diradmins` (you) can read the directory admin password file `/etc/linux-iam-lab/ldap-admin.pw`. Never paste it into chats or tickets.
