SSH is how administrators and automation reach Linux servers. For IAM, SSH **keys are credentials**: they must be issued, inventoried, reviewed and revoked like passwords.

## Keys in one minute

- `ssh-keygen -t ed25519` creates a **key pair**: a *private key* (`~/.ssh/id_ed25519`, never leaves its owner, ideally protected by a passphrase) and a *public key* (`id_ed25519.pub`, safe to share).
- The server lists accepted public keys, one per line, in the user's `~/.ssh/authorized_keys`.
- On login, the client proves it holds the private key; the server checks the public key is listed. No password crosses the network.
- A key's **fingerprint** (`ssh-keygen -lf key.pub`) is a short hash used to verify it over another channel ("read me the fingerprint").

```text
256 SHA256:3xR9...kQ btran@laptop (ED25519)
```

## Permissions matter (StrictModes)

sshd ignores `authorized_keys` if anyone other than the user (or root) could change it:

| Path | Owner | Mode |
|---|---|---|
| home directory | the user | not group/world-writable (e.g. `750` or `755`) |
| `~/.ssh` | the user | `700` |
| `~/.ssh/authorized_keys` | the user | `600` |

The client side has the same rule for private keys (`chmod 600`). Windows OpenSSH checks the file's ACL instead.

## Host keys and fingerprints

The **server** also has a key pair. The first time you connect, your client shows the server's fingerprint and asks you to confirm it; afterwards it is remembered in `~/.ssh/known_hosts`. A changed host key produces a loud `REMOTE HOST IDENTIFICATION HAS CHANGED` warning - possibly an attack; never just delete the line without checking. On the server: `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub`.

> **Windows** This lab pinned the VM's host key for you at install. In Windows Terminal, `ssh linux-iam-lab` uses it; the fingerprint is shown on the portal's *Progress & lab tools* page.

## Server configuration

- Main file `/etc/ssh/sshd_config`; drop-in files `/etc/ssh/sshd_config.d/*.conf` are read first, in name order, and **the first value found for a setting wins**.
- `sudo sshd -t` validates the configuration (no output = OK). **Always run it before reloading.**
- `sudo sshd -T` prints the *effective* configuration; `sudo sshd -T -C user=btran,host=laptop,addr=10.0.2.2` evaluates `Match` blocks for a hypothetical connection.
- `sudo systemctl reload ssh` applies changes; existing sessions stay connected.

Useful settings: `PermitRootLogin no`, `PasswordAuthentication no`, `PubkeyAuthentication yes`, `MaxAuthTries 3`, `AllowGroups ssh-users`, `LoginGraceTime 30`, `X11Forwarding no`, `RevokedKeys /etc/ssh/revoked_keys`.

## Diagnosing failed SSH logins

| Symptom | Look at |
|---|---|
| `Permission denied (publickey)` | server log: `sudo journalctl -u ssh -n 30` (or `/var/log/auth.log`) |
| `Authentication refused: bad ownership or modes` | home / `.ssh` / `authorized_keys` permissions |
| `User x from y not allowed because not in any group` | `AllowGroups` / `AllowUsers` |
| `User account has expired` / `account locked` | `chage -l`, `passwd -S` |
| `This account is currently not available` | shell is `nologin` |
| client side details | `ssh -v user@host` (more `v` = more detail) |

> **Careful** Before changing sshd on a remote server, keep an existing session open and test a **new** login from a second window. If you lock yourself out in this lab you still have the portal's web terminal (it does not use SSH) and `lab rescue sshd`.
