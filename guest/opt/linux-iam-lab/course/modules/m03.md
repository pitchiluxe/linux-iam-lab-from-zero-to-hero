In IAM, an identity goes through a **lifecycle**: a **joiner** gets an account and the right roles, a **mover** changes roles (and must *lose* the old ones), and a **leaver** is disabled promptly and cleanly. On a Linux server that lifecycle is managed with a handful of commands and three files.

## The three identity files

| File | Readable by | One line per | Key fields |
|---|---|---|---|
| `/etc/passwd` | everyone | account | `name:x:UID:GID:comment:home:shell` |
| `/etc/group` | everyone | group | `name:x:GID:member1,member2` (supplementary members) |
| `/etc/shadow` | root and group `shadow` only | account | `name:hash:lastchange:min:max:warn:inactive:expire:` |

```text
btran:x:2003:2003:Ben Tran - Software Engineer:/home/btran:/bin/bash
engineering:x:3003:btran,enovak
btran:$y$j9T$...:20403:0:99999:7:::
```
- **UID** (user ID) is what the kernel actually checks. Names are labels for humans. Two accounts with the same UID are the *same* identity to the kernel - an audit finding.
- **UID ranges** on Ubuntu: `0` is root; `1-999` are system/service accounts; `1000+` are people. This lab uses `2001+` for staff and `10001+` for directory users.
- A password hash starting with `!` or `*` means the password is **locked** or never set. The 8th shadow field is the **account expiry** day (days since 1970-01-01).

## Groups are roles

- Every user has one **primary group** (the GID in `/etc/passwd`). New files get this group. Ubuntu creates a private group with the same name as the user ("user private group").
- **Supplementary groups** (listed in `/etc/group`) are how you grant roles: put `jkim` in `finance` and she gets whatever `finance` can do.
- Group changes apply to **new logins**. A user already logged in must log out and back in (or run `newgrp`). `id USER` reads the database, so it shows the change immediately.

## Lifecycle commands

| Task | Command |
|---|---|
| inspect | `id btran`, `getent passwd btran`, `getent group finance`, `groups btran`, `sudo chage -l btran`, `sudo passwd -S btran` |
| create a user | `sudo useradd -m -c "Full Name - Role" -s /bin/bash -G finance jdoe` (`-m` home, `-c` comment, `-s` shell, `-G` supplementary groups, `-e YYYY-MM-DD` expiry) |
| set a password | `sudo passwd jdoe` |
| force change at next login | `sudo chage -d 0 jdoe` |
| add a role | `sudo usermod -aG webops btran` (**`-a` append is essential**: `-G` alone *replaces* all supplementary groups) or `sudo gpasswd -a btran webops` |
| remove a role | `sudo gpasswd -d btran engineering` |
| expiry | `sudo chage -E 2027-06-30 jdoe`; `-E -1` removes it; `-E 0` expires now |
| lock / unlock password | `sudo usermod -L jdoe` / `sudo usermod -U jdoe` (key-based SSH still works when only the password is locked!) |
| block interactive shell | `sudo usermod -s /usr/sbin/nologin jdoe` |
| create a group | `sudo groupadd webops` |
| delete (only after retention) | `sudo userdel -r jdoe` (`-r` also removes the home folder) |

> **Careful** `usermod -G webops btran` without `-a` removes btran from every other supplementary group. Always re-check with `id btran` after a change.

## Disabling vs deleting

Organisations usually **disable** a leaver first (lock, expire, remove roles, kill sessions, keep data) and **delete** after a retention period. Deleting immediately loses evidence and can leave **orphaned files** owned by a bare UID that a future account could inherit.

## Lockout

This lab's Ubuntu uses **pam_faillock**: after 5 failed passwords within 15 minutes an account stays locked until an administrator resets it (`unlock_time = 0` in `/etc/security/faillock.conf`). `sudo faillock --user NAME` shows the failures; `sudo faillock --user NAME --reset` clears them. Unlock only after the identity of the requester is verified.

> **Careful** This applies to you too: five wrong passwords at the `sudo` prompt lock `student`. If that happens, use **Progress & lab tools > Unlock student** in the portal (or `lab rescue faillock`).
