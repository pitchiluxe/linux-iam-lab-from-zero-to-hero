Groups decide **who** has a role; file permissions decide **what** that role can touch. Every "I can't open the share" ticket ends here.

## Reading `ls -l`

```text
-rw-r----- 1 aokafor finance 812 Nov 11 10:00 payroll.csv
drwxrws--- 2 root    finance 4096 Nov 11 10:00 finance-team
```
| Part | Meaning |
|---|---|
| first character | `-` file, `d` directory, `l` symbolic link |
| next 9 characters | three triplets: **u**ser (owner), **g**roup, **o**thers - each `r` read, `w` write, `x` execute |
| `aokafor finance` | owner and group |

The kernel checks **one** triplet: owner if you are the owner; else group if you are in the group; else others. It does not "add them up".

## What r, w, x mean

| | On a file | On a directory |
|---|---|---|
| `r` | read the content | list the names inside (`ls`) |
| `w` | change the content | create, delete, rename entries inside |
| `x` | run it as a program | **enter / pass through** it (`cd`, or reach anything below it) |

To open `/srv/a/b/file.txt` you need `x` on `/srv`, `/srv/a`, `/srv/a/b` **and** `r` on the file. `namei -l /srv/a/b/file.txt` shows every step - the fastest way to find the broken link in the chain.

## Changing permissions

Numeric (octal): `r=4, w=2, x=1`, add them per triplet.

| Mode | Means | Typical use |
|---|---|---|
| `640` | `rw-r-----` | confidential file: owner edits, group reads |
| `660` | `rw-rw----` | team-editable file |
| `750` | `rwxr-x---` | private folder the group may enter and list |
| `2770` | `rwxrws---` | shared team folder (`2` = setgid, see below) |

Symbolic: `chmod g+w file`, `chmod o-rwx dir`, `chmod u=rw,g=r,o= file`, `chmod -R g+rX dir` (`X` = execute only on directories).

Ownership: `sudo chown aokafor:finance payroll.csv` (owner and group), `sudo chgrp finance file`.

## Special bits

- **setgid on a directory** (`chmod g+s`, the `2` in `2770`): new files inside get the directory's **group** instead of the creator's primary group. Essential for team folders.
- **sticky bit** (`chmod +t`, `1777` on `/tmp`): in a writable folder, only a file's owner can delete it.
- **setuid on a program** (`4755`, e.g. `/usr/bin/passwd`): it runs with the owner's (root's) privileges. Unexpected setuid files are a red flag: `find / -perm -4000 -type f 2>/dev/null`.

## umask

`umask` removes permissions from new files. With the default `022`, new files are `644` and folders `755` - **others can read**. With `027` new files are `640`. Check with `umask`; it is set per user/session (for example in `~/.profile` or `/etc/login.defs`).

## ACLs (access control lists)

When owner/group/others is not enough - "the auditor needs read access, but must not join HR" - add named entries:

```linux
sudo setfacl -m u:rmorgan:r-- /srv/hr/reviews/2026-q4.txt
getfacl /srv/hr/reviews/2026-q4.txt
```
```text
user::rw-
user:rmorgan:r--
group::rw-
mask::rw-
other::---
```
- `-m` modify/add, `-x` remove an entry, `-b` remove all ACLs, `-R` recursive, `-d` set the **default** ACL that new files in a directory inherit.
- A `+` at the end of the `ls -l` mode (`-rw-rw----+`) means "this file has an ACL - run `getfacl`".
- The **mask** caps what named users and groups can get. `chmod g-w` on a file with an ACL lowers the mask.

## Test as the user

Always prove access with the real identity: `sudo -u btran cat FILE` (allowed?) and `sudo -u dpatel cat FILE` (denied?). Two users, two results - that is your evidence.
